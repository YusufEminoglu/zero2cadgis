How to use this manual. Each section documents one subsystem of the plugin. The manual is organised by engine (CAD, GIS, NCZ) rather than by format, because each engine defines a distinct conversion pipeline with its own parameters, caching, and output behaviour. Cross-references in bold link related sections. Parameter names and field names are in monospace. All CRS codes are from the EPSG registry as read from the PROJ database.

1. Architecture & Design

Plugin Overview & Design Philosophy

02CadGis is a professional QGIS dock plugin for converting CAD and GIS exchange files into clean, styled GeoPackage layers. It is built for planning, cadastral, municipal, and urban-analytics workflows where AutoCAD DWG/DXF, Netcad NCZ/NCA, KML/KMZ, GML, GeoJSON, CSV/TSV, SpatiaLite, GPX, DGN, FileGDB, and Personal GDB (.mdb) files need to become usable QGIS data quickly and accurately.

The plugin's design rests on five principles:

  1. No data loss. Every feature that can be read is written. Features with geometry problems are repaired, not dropped. Empty/non-spatial entities are filtered with a logged warning, not a fatal error.
  2. Selective conversion. The layer tree shows you what is in the file before conversion. You check only the layers you need; unchecked layers cost zero decode time.
  3. Format-native parsing where GDAL falls short. The plugin has its own NCZ parser, its own DGN v8 reader, its own CSV sniffer, and its own MS Access reader — each stepping in when the GDAL/OGR driver for that format is missing, slow, or incomplete.
  4. Turkish planning data is a first-class citizen. The CRS detector knows every EPSG code Turkish survey data uses. The PlanGML engine applies the official Ministry e-Plan symbology. The mojibake repairer recovers Turkish characters from mis-encoded CAD layers.
  5. Progressive disclosure. The dock panel shows only the controls relevant to the selected input type. Drag-and-drop auto-detects the format and jumps to the right tab.

2. CAD Converter Engine

Engine Overview: DXF, DWG & DGN

The CAD engine handles three AutoCAD-family formats and one MicroStation format. For DXF and DGN (with GDAL driver), the pipeline is: GDAL/OGR read → split by CAD layer → geometry coercion (3D→2D flattening, curve segmentization, single↔multi conversion) → collinear simplification → CRS transform → output.

The engine's CadCleanupEngine (core/cad_engine.py) provides three post-processing steps applied to every CAD-sourced layer:

  1. Duplicate vertex removal: consecutive points within 0.0001 map units of each other are collapsed to one.
  2. Collinear simplification: intermediate vertices lying on a straight line between their neighbours are removed. Iterative: continues until no more collinear vertices remain.
  3. Polygon gap closure: open polygon rings are closed by snapping endpoints within a user-configurable tolerance.

These steps reduce the vertex count of CAD drawings (which routinely contain hundreds of redundant collinear nodes along straight walls and roads) by 50–90%, dramatically reducing GeoPackage size and rendering time without changing the geometry's visual appearance.

CAD Layer Splitting (by Layer / Level)

When Split into CAD layers is enabled (the default for DXF and DGN sources), the engine reads the source file's internal layer structure — DXF Layer names or DGN Level numbers — and presents each as a separate checkable row in the layer tree. Each row shows the layer name, the geometry type(s) it contains, and the feature count.

When splitting is disabled, all geometry is merged into a single layer per geometry type (points, lines, polygons). This is faster but loses the layer-name metadata that often encodes land-use categories.

Geometry coercion (_coerce_geometry_for_layer) handles three compatibility issues automatically:

  • 3D → 2D flattening: CAD features with Z coordinates are projected to 2D (Z dropped) so QGIS memory layers accept them.
  • Curve segmentization: circular arcs, ellipses, and splines are approximated as straight-line segments.
  • Single ↔ Multi conversion: a single Polygon in a MultiPolygon layer is auto-promoted via convertToMultiType(); a MultiPolygon in a Polygon layer is auto-demoted via convertToSingleType().

Collinear Simplification & Geometry Cleanup

The CadCleanupEngine applies a vertex-thinning algorithm that preserves the visual shape of CAD geometry while eliminating the dense collinear nodes that CAD software places at every snap point. The process has two stages:

Stage 1 — Duplicate removal: For each coordinate sequence, any point whose (x, y) is within 10⁻⁴ map units of its predecessor is dropped.

Stage 2 — Collinear removal: For each triplet of consecutive points (A, B, C), the cross product of vectors AB and BC is computed. If the cross product is below a threshold (meaning A, B, C are effectively collinear), point B is removed. The process iterates until a pass finds no removable points.

CAD vertex density. A single straight wall in a DXF file may contain 20–50 collinear vertices from construction-snap points. After simplifcation, it contains 2 (the endpoints). The visual appearance is identical; the file size and rendering performance improve dramatically.

AutoCAD DWG: Native GDAL & ODA File Converter

DWG support is the most complex format pathway in the plugin, combining three fallback layers:

LayerDWG VersionsMechanism
1. GDAL libopencadR2000 and earlierGDAL's built-in CAD driver reads legacy DWG directly via ogr.Open(). If the driver reports layers, they are used immediately.
2. ODA File ConverterR2004–R2024 (modern)The Open Design Alliance (ODA) provides a free command-line ODAFileConverter tool. 02CadGis searches for it in: QSettings, QGIS settings, PATH, environment variables, Windows registry, and common installation paths. If found, the DWG is converted to DXF via a temporary ASCII-safe filename (to handle Turkish/Unicode paths), then the DXF is read normally. An interactive setup dialog appears if ODA is not found.
3. LibreDWG dwg2dxfVariousIf ODA is not available, the plugin falls back to the open-source dwg2dxf from the LibreDWG project as a last resort.

The ODA integration search order is documented and deterministic. A "ODA Path…" button on the CAD panel lets the user manually point to the ODAFileConverter.exe executable, and the path is persisted in QGIS settings.

DGN v8: Pure-Python Fallback Reader

When GDAL's DGNv8 driver is unavailable (common on Linux and older QGIS builds), the plugin activates its own pure-Python DGN v8 reader (core/dgn_v8_reader.py). This module:

  1. Opens the DGN file as an OLE2 compound document using the vendored olefile library (_vendor/olefile.py).
  2. Locates the element streams within the OLE2 storage.
  3. Decompresses the streams (zlib).
  4. Parses each element by type: Line (type 3), LineString (type 4), Shape/Polygon (type 6) are fully supported. Complex containers (cell headers, complex strings/shapes) and annotations (text, dimensions) are skipped for geometry but their Level, colour, and style attributes are reported via placeholder centroid/bounding-box geometry.
  5. Groups elements by DGN Level, presenting each Level as a selectable CAD layer in the layer tree — the same workflow as DXF.

Coordinates are returned as double-precision values in master units (metres, survey-feet) with no scaling applied. The caller is responsible for CRS selection.

GDAL first, pure Python as fallback. The GDAL path is always tried first. Only when ogr.Open() returns None on a .dgn file does the pure-Python reader activate. This ensures maximum fidelity when the GDAL driver is available and graceful degradation when it is not.

3. GIS Converter Engine

Engine Overview: KML, GML, GeoJSON, CSV, GDB & More

The GIS engine handles all OGR-supported vector exchange formats plus delimited text. The pipeline is: format-specific pre-processing → OGR read → layer tree population → CRS transform → optional attribute expansion → output.

Format-specific pre-processing steps:

FormatPre-Processing
KMZExtracted to a temporary directory. Every .kml file inside the ZIP is opened, not just the first. KML balloon HTML tables and <description> list items are expanded into real attribute fields.
KML GroundOverlayWhen the extraction toggle is on, <GroundOverlay> elements are converted to georeferenced GeoTIFF files using GDAL and added to the QGIS project as raster layers.
CSV/TSV/TextSniffed for delimiter (comma, tab, semicolon, pipe), encoding, and geometry columns (X/Y or lon/lat pairs, or a WKT column). See CSV Sniffer.
FileGDB (.gdb)Opened via GDAL's OpenFileGDB driver. In live mode, layers are added as zero-copy references. The layer catalog is cached by content fingerprint.
Personal GDB (.mdb)Read via the plugin's own MS Access reader when GDAL's PGeo driver is unavailable. See MS Access Reader.

CSV/TSV Text Sniffer: Auto-Detection

The CSV Sniffer (core/csv_sniffer.py) automatically detects the structure of delimited text files. It samples the first 100 lines of the file and determines:

PropertyDetection Method
DelimiterTries comma, tab, semicolon, and pipe. The delimiter that produces the most consistent column count across the sample wins.
EncodingAttempts UTF-8, then falls back to the system locale encoding.
X (Longitude) columnSearches column headers for x, lon, longitude, easting, X_COORD (case-insensitive). When found, checks that values are numeric and within plausible coordinate ranges.
Y (Latitude) columnSearches for y, lat, latitude, northing, Y_COORD.
WKT columnSearches for wkt, geom, geometry. When found, checks that the first non-empty value starts with a WKT type keyword (POINT, LINESTRING, POLYGON, etc.).
CRS suggestionIf the X values are in the range (−180, 180) and Y in (−90, 90), EPSG:4326 is auto-suggested.

All auto-detected values are presented in the UI and can be manually overridden before import.

KMZ: Multi-Document Import & GroundOverlay Extraction

Standard OGR KMZ import reads only the first KML document inside the ZIP archive (doc.kml). 02CadGis extracts the entire KMZ to a temporary directory and opens every .kml file found, merging all documents into the layer tree. This ensures multi-document archives — common in municipal planning submissions — are imported in full.

KML Balloon HTML expansion: KML Placemark <description> elements often contain HTML tables and lists. The engine parses these and creates real attribute columns for each key-value pair found in the HTML, making the data queryable in QGIS.

GroundOverlay → GeoTIFF: When enabled, <GroundOverlay> elements (georeferenced images draped on the terrain) are extracted and saved as GeoTIFF files using their KML <LatLonBox> bounds for georeferencing. These are added to the QGIS project as raster layers alongside the vector output.

Geodatabase: Live Zero-Copy Load & Catalog Cache

File Geodatabase (.gdb) and Personal Geodatabase (.mdb) sources support a Live output mode that adds checked layers directly to QGIS as zero-copy references — the data stays in the Geodatabase file; QGIS reads it on demand. This means even multi-million-feature layers open almost instantly (benchmarked at ~0.27 seconds for 4.27 million features across two layers from a municipal FileGDB).

Catalog cache (core/ogr_catalog_cache.py): The layer list of Geodatabase and database sources is cached locally, keyed by a content fingerprint (file size + modification time). Reopening the same unchanged .gdb or .mdb lists its layers from cache — 100×+ faster than reopening the driver, which for a large Geodatabase can take 10–30 seconds just to enumerate layers. The cache auto-invalidates when the file changes.

MS Access / Personal Geodatabase (.mdb) Reader

When GDAL's PGeo driver is unavailable (common on Linux and newer QGIS builds where the MDB driver was removed), the plugin activates its own pure-Python MS Access reader (core/msaccess_reader.py). This module:

  1. Opens the .mdb file as a Jet database using the vendored mdbtools-compatible reader or the system's mdb-export utility.
  2. Enumerates the tables, identifying those with geometry columns.
  3. Reads each spatial table's features and presents them as selectable layers.

4. Netcad NCZ Engine v2

Engine v2: Architecture & Design

The NCZ Engine v2 (core/ncz_engine/v2/) is a ground-up rewrite of the Netcad binary format parser. It is an independent, block-oriented decoder that reads NCZ files without any dependency on the Netcad software or libraries. The engine was verified bit-for-bit identical to the previous engine across a synthetic NCZ corpus and validated against a real 8,163-entity municipal Netcad drawing.

The v2 engine splits the parsing task into five cooperating modules:

ModuleFileResponsibility
Binary Readerbinary.pyBounds-checked binary stream reader. Every read operation validates offset and length against the file size before accessing the underlying bytes. This is the security boundary: no read can overrun the buffer.
Parserparser.pyFile header parsing, block index construction, and dispatch to specialized decoders based on block type.
Geometry Decodergeometry.pyRegistry of geometry-type decoders. Each NCZ entity type (point, line, polyline, circle, arc, text, block reference, etc.) has a registered decoder that reads the entity's binary record and produces a QGIS-compatible geometry and attribute set.
Attribute Decoderattributes.pyDecodes @TAB attribute tables, which store tabular data linked to geometry entities by name or label fields.
Block Catalogueblocks.pyMaintains the catalogue of NCZ blocks — reusable geometry definitions referenced by block-reference entities. Resolving a block reference means looking up the block definition and instantiating its geometry at the reference's insertion point, scale, and rotation.

Lazy Layer Catalog & Selective Decode

The v2 engine's key performance innovation is the lazy catalog: when you select a drawing file, the engine reads only the file header and block index — it does not decode any geometry. The layer tree (CAD layer names, entity counts per layer, entity types) is built from the index alone, which is near-instant even for large municipal files.

Geometry is decoded only for the layers you keep checked at import time. Unchecked layers cost zero decode time. This means a drawing with 50 CAD layers where you only need 5 pays only the cost of decoding those 5.

Fingerprinted Index Cache

The layer catalog of each drawing is cached to disk (core/ncz_engine/v2/cache.py), keyed by the file's absolute path + file size + modification time (a content fingerprint). Reopening an unchanged drawing shows its layer tree from cache — no file read, no index parse — benchmarked at ~160× faster on a real 1.2 MiB municipal file.

The cache auto-invalidates when the file size or modification time changes. A Clear cache button on the Netcad panel allows manual cache reset.

Automatic CRS Detection: Turkish Projection Families

A Netcad drawing stores its own SRS id (e.g. SRS=7936) — this is not an EPSG code and must never be used as one. The drawing also stores a human-readable projection string such as ITRF / 3 / Zone 42 or ED50 / 3 / Zone 33.

The CRS detector (core/crs_detect.py) combines two independent signals to name the EPSG code exactly:

  1. Projection text → gives the datum (TUREF vs ED50 vs WGS 84) and the zone/central-meridian hint. TUREF and ED50 differ by ~200 m over the same ground — impossible to distinguish from coordinates alone.
  2. Easting magnitude → gives the axis convention. A 6-digit easting (~500,000) is the TM form (false easting 500,000, no zone prefix). An 8-digit easting (e.g. 3,542,000) is the 3-degree Gauss-Krüger form where the zone number is baked into the easting itself (zone × 1,000,000 + 500,000).

The detector covers every EPSG code in the Turkish survey projection families:

FamilyTM Form (6-digit easting)GK Form (8-digit easting)Zones
TUREF / 3-degree TMEPSG:5253–5259EPSG:5269–527527, 30, 33, 36, 39, 42, 45
ED50 / 3-degree TMEPSG:2319–2325EPSG:2206–221227, 30, 33, 36, 39, 42, 45

The detected CRS is pre-selected in the CRS dropdown but not locked — the user can override it. When the drawing does not contain enough information to name a CRS with confidence (missing projection string AND ambiguous coordinate range), the detector leaves the selection empty and the panel explains what is missing rather than guessing. A wrong CRS silently puts data in the wrong place, and the detector's philosophy is: no CRS is better than a wrong CRS.

Northing sanity check. The detector also checks that sample coordinates fall within Turkey's northing band (~3.8–4.8 million metres). Coordinates outside this range indicate the drawing is not in a Turkish projection and the detector reports "unknown" rather than misidentifying the zone.

Batch Import, Layer Selection & Geometry Metrics

The Netcad panel supports selecting multiple NCZ/NCA files simultaneously. Each file's layers and @TAB tables are shown in the tree with the filename as a parent node. By default, file groups are kept separate — layers from different drawings are not merged. When Merge geometry types is enabled, layers with the same name inside the same geometry-type group are merged across files.

Geometry metrics (optional): when enabled, three computed fields are added to each output layer:

  • ncz_length — feature length (for lines) or perimeter (for polygons), in map units.
  • ncz_area — feature area (for polygons), in map units².
  • ncz_centroid_x, ncz_centroid_y — centroid coordinates in map units.

@TAB Attribute Tables & Joins

NCZ drawings may contain @TAB tables — attribute tables stored inside the drawing file, linked to geometry entities by name or label fields. The engine decodes these tables and presents them in the tree alongside CAD layers. When both a CAD layer and its matching @TAB table are checked, the engine performs an attribute join: the table columns are appended to the geometry layer's attribute table, matched on the entity name/label field.

This preserves the drawing's internal data model: geometry carries spatial information; @TAB tables carry the alphanumeric attributes (land-use codes, parcel IDs, building heights, etc.).

5. PlanGML Mode & Official Symbology

PlanGML Mode Overview

PlanGML mode (off by default) transforms a raw CAD drawing into a standards-compliant spatial plan. When enabled, three things happen:

  1. Tabaka are grouped into the Ministry's official upper groups (KONUT ALANLARI, TICARET ALANLARI, EGITIM TESISLERI ALANI, etc.) rather than raw CAD layer names.
  2. PlanGML schema columns are populated with the official upper-group, sub-group, detail-group, and function codes from the Mekânsal Planlar Yapım Yönetmeliği (MPYY) UIP database.
  3. Official e-Plan symbology is applied: each tabaka is drawn with its Ministry-defined fill colour, stroke, hatch pattern (tarama), and label style — the same gösterim used on the e-Plan portal at eplan.csb.gov.tr.

The gösterim data (350+ rules and 131 tarama tiles) is compiled into the plugin — nothing is downloaded, no style server is needed, and the plugin works fully offline. The symbology database is stored in symbology-style.db (888 KB SQLite) and the rules are defined in core/symbology.py.

Attribution. The gösterim is the official standard of the Turkish Ministry of Environment, Urbanisation and Climate Change, reproduced under the terms documented in THIRD_PARTY_NOTICES.md. The plugin does not redistribute any official font files. See Appendix D.

Plan Type Auto-Detection from Scale

The plan type (UIP 1/1000, NIP 1/5000, CDP 1/25,000+) is detected from the drawing's file name using pattern matching:

  • Files containing UIP, uip, 1000, 1/1000, or uygulama → UIP (1/1000)
  • Files containing NIP, nip, 5000, 1/5000, or nazim → NIP (1/5000)
  • Files containing CDP, cdp, 25000, 1/25000, cevre, or cevre duzeni → CDP (1/25,000+)

The detected type can be manually overridden before import.

CAD Color Preservation, Labels & Styling

CAD drawings carry per-entity colour intent (ACI — AutoCAD Color Index, or ARGB values in Netcad). The plugin preserves this intent in QGIS:

  • Netcad ARGB colours: when the Colors toggle is on, each feature's ncz_color attribute is read and a categorised renderer is applied to the layer, with one symbol category per unique colour value. The renderer uses the exact ARGB values from the drawing.
  • CAD text labels: when the Labels toggle is on, text entities in the drawing are rendered as QGIS labels using QgsPalLayerSettings. The label column is chosen by finding one that actually contains text (not merely exists and is empty on every feature — a historical bug where labelling latched onto an empty column). Point layers that carry text draw a small 0.6 mm anchor marker instead of a full symbol, so the text is what you read.
  • Plan areas outline: in PlanGML mode, plan-area polygons receive a 0.7 mm outline even when the official style set leaves the outline off — the fill or tarama carries the meaning, but a plan sheet needs its function boundaries to read visually.

Turkish Mojibake & Unicode Character Repair

CAD files produced by Turkish municipal software frequently contain mojibake — Turkish characters (Ğ, Ş, İ, ı, ğ, ş, ç, ö, ü) corrupted by incorrect encoding conversions. The fix_mojibake engine (core/cad_engine.py) applies multi-pass encoding recovery:

  1. UTF-8 decode attempt — if the bytes are valid UTF-8, they are kept as-is.
  2. CP1254 (Turkish Windows) decode — common for Turkish CAD software.
  3. CP1252 (Western Windows) decode — common when Turkish characters were written through a non-Turkish locale.
  4. ISO-8859-9 (Turkish Latin) decode — the ISO Turkish encoding.
  5. Direct character replacement mapping — for stubborn sequences that survive all encoding passes, a lookup table maps known corrupted byte pairs to their correct Turkish characters.

The repair is applied to: CAD layer names, DXF Level names, feature attribute values, label text, and UI tree item labels. The \U+XXXX Unicode escape sequences sometimes found in DXF files are also unescaped to their actual characters.

Format-Specific Details & Limitations

FormatKnown Limitations
DWGModern DWG (R2004+) requires ODA File Converter or LibreDWG — neither is bundled. The plugin searches for them and provides setup guidance. Legacy DWG (R2000−) reads via GDAL's libopencad driver, which may not be compiled into all QGIS distributions.
DGN v8Pure-Python reader does not support complex cell geometry, text elements, or dimension elements as full geometry — these are represented by placeholder points. For full fidelity, install a QGIS build with the DGNv8 GDAL driver.
NCZ/NCANCZ Engine v2 is a reverse-engineered parser validated against a real municipal drawing corpus. Drawings produced by very old or very new Netcad versions may use block types not yet in the decoder registry — these are skipped with a warning, not a crash.
KMZOnly KML documents inside the ZIP are read. Other file types (images, schemas) inside the archive are ignored unless they are referenced by a GroundOverlay element.
GDB/MDBLive mode adds layers in their native CRS without transformation. Use GeoPackage or Scratch mode if CRS reprojection is needed.
CSV/TSVThe sniffer reads only the first 100 lines. If geometry columns appear after line 100, they must be manually selected. Files with mixed delimiters (e.g. commas inside quoted fields) may require manual override.

Appendix C: Glossary

TermDefinition
ACI (AutoCAD Color Index)A palette of 255 indexed colours used in DXF/DWG files. The plugin maps ACI values to RGB for QGIS rendering.
CAD layer / LevelA named grouping of entities within a CAD drawing. DXF calls them Layers; DGN calls them Levels. The plugin splits drawings by this grouping.
Collinear simplificationRemoving intermediate vertices that lie on a straight line between their neighbours. Reduces vertex count without changing geometry appearance.
CRS (Coordinate Reference System)The projection and datum that give spatial meaning to coordinate values. Identified by EPSG codes.
e-PlanThe Turkish Ministry's electronic plan submission portal (eplan.csb.gov.tr). The source of the official gösterim standards.
EPSGA public registry of geodetic parameters (projections, datums, coordinate systems), each identified by a unique integer code.
GDAL/OGRThe Geospatial Data Abstraction Library. QGIS's vector (OGR) and raster (GDAL) I/O backbone. The CAD and GIS engines use OGR for most formats.
GeoPackage (.gpkg)An open, SQLite-based format for geospatial vector and raster data. The plugin's default durable output format.
GösterimTurkish: the official visual representation (colour, hatch, line type) of a plan function as defined by the Ministry.
GroundOverlayA KML element that places an image draped over the terrain at specified geographic coordinates.
Live (zero-copy) modeAdding a layer to QGIS by referencing the source file directly, without conversion. The data stays in the source; QGIS reads it on demand.
MojibakeGarbled text resulting from interpreting bytes in the wrong character encoding. Turkish CAD files frequently exhibit CP1254↔CP1252↔UTF-8 mojibake.
MPYYMekânsal Planlar Yapım Yönetmeliği — Turkish Spatial Planning Regulation. Defines the official UIP tabaka catalog.
NCZ / NCANetcad's native binary drawing formats. NCZ is the standard format; NCA is a compatible variant.
ODA (Open Design Alliance)An industry consortium providing a DWG-compatible file converter. The plugin uses ODAFileConverter for modern DWG versions.
OLE2Microsoft's Compound Document format. Used by DGN v8 files as their container.
PASE (PlanX Adaptive Symbology Engine)The plugin's symbology engine that matches CAD tabaka to official e-Plan gösterim rules.
PlanGMLThe Turkish Ministry's XML-based spatial plan data standard. The plugin populates PlanGML schema columns from the tabaka catalog.
Scratch layerA temporary QGIS memory layer. Exists only for the current session; not written to disk.
SRS idA Netcad-internal coordinate system identifier. Not an EPSG code and must never be used as one.
TabakaTurkish: layer. In planning context, a named category of spatial features (e.g. PL_KONUT, PL_YOL) defined by the MPYY.
TaramaTurkish: hatch pattern. An official tile image used as a polygon fill pattern for certain plan functions.
@TABNetcad's internal attribute table format, stored inside NCZ files. Linked to geometry entities by name/label.
